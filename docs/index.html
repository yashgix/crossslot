Scope. Sim does not support Redis Cluster today. That is what issue #9734 asks for. These are compatibility findings for that request, not production bugs. They show what fails when Sim's Redis code is pointed at a cluster.

Why a cluster changes behaviour

A cluster splits the key space into 16,384 hash slots, and each primary owns a range of them. A key's slot is a hash of its name. The rule that matters here: each multi-key command, Lua script and transaction needs all its keys in one slot. If they are not, the server answers CROSSSLOT. If the keys live on different nodes, a command sent to the wrong node gets MOVED. An explicit ioredis pipeline in cluster mode is not split across nodes. Its keys must fall in one slot allocation group, and ioredis refuses the pipeline before sending anything if they do not.

Standalone Redis has none of these rules, so code that works there can fail on a cluster with no change.

InterpretationThe failing key sets tested here lack a common hash tag and span slots in this configuration. A hash tag is a part of the key in braces, {like this}. When a key has one, only that part is hashed, so keys with the same tag share a slot. That is the usual way to keep related keys together.

If Sim implements #9734

InterpretationThese are options a maintainer could weigh, not a finished fix. The repository applies one candidate change to a copy of the code to see what it would take. It is tested only by this harness.

  • Hash tags so the keys of one operation share a slot, for example the queue's list and heartbeat keys under one tag. Renaming keys orphans the old ones, and old and new versions do not share state during a rolling deploy.
  • Split multi-key scripts and pipelines into per-key calls where atomicity is not needed, such as the MGET in the usage segment cache.
  • Rework operations whose keys cannot share a tag. The room manager's MULTI at redis-manager.ts:243 touches room keys and socket keys, and a socket belongs to several rooms. In the candidate change it becomes two transactions, and removal and activity updates stop being atomic across the two.
  • Declare every key a script touches. The hosted queue's script builds a heartbeat key inside the script.

The candidate change leaves 1 site failing (the token bucket's multi-bucket script) and 2 features it cannot verify. See Technical details.

Limitations

  • The counts are failing Redis operations, not application crashes. Sim catches several of these errors and fails open with warnings.
  • Zero mismatches does not mean equal behaviour. A failed operation skips the comparison with the standalone result.
  • The harness drives Sim's extracted Lua scripts and key builders through the same client libraries (ioredis 5.11.1, within Sim's ^5.6.0, and node-redis 5.10.0, exact). It does not run Sim's whole application.
  • The reproductions inject a cluster client into Sim's unchanged methods, because Sim has no cluster option.
  • The harness's classifier counts any Redis reply error as a Sim failure before it checks for harness errors. No effect was found on these results, but it is a limitation.
  • The harness repairs some failed writes with single-key commands so that later sites are exercised. Unrepaired failures also suppress later comparisons involving the affected entities. XREAD blocking waits are omitted. Timing, concurrency and pub/sub compatibility are not established.
  • One Redis version (8.10.3), one machine, one pinned Sim commit.

Technical details

Method, results and data

Numbers come from results/before.json, results/after.json, results/summary.txt and results/repro/. Measured facts, interpretation and limitations are labelled.

Method

  • Corpus. The Sim files the tool reads are a pinned set of 175 files at commit edf5f0a47da8147466cb893c0a1666058331d42e, fetched from GitHub and checked against SHA-256 hashes in data/MANIFEST.sha256. All 175 match.
  • Scan. A scanner reads the corpus and lists Redis calls it can analyse (eval, evalsha, multi, pipeline, multi-key commands). Recognised calls whose scripts or keys cannot be resolved are reported as UNRESOLVED. Unsupported call syntax, for example redis["eval"](...), can be missed.
  • Drivers. 13 drivers each replay one Sim feature: its real Lua scripts and key builders, through ioredis 5.11.1 or node-redis 5.10.0. Each runs 20 seeds of 500 operations, 10,000 operations per feature and 130,000 in total.
  • Same stream, two targets. The same seeded operation stream runs on a standalone Redis and on a 6-node cluster, both Redis 8.10.3, started by npm run cluster:up from compose.yaml.
  • A failing site. A call site counts as failing when Redis or the cluster client refuses a call made at that site. A site that never ran does not count. A control feature uses only single-key scripts and must report 0 failures.
  • After the patch. The candidate change is applied to a copy of the corpus and the same run is repeated, with the unpatched corpus as the reference. A replacement call under a condition the harness cannot evaluate is unverifiable and never counts as a pass.

MeasuredScanner against run, on executed sites: 0 false positives, 0 false negatives (scanner in both result files).

InterpretationThe MOVED comes from node-redis sending the whole MULTI to the node that owns the first key's slot. The session key belongs to another node and a redirect cannot be followed inside a transaction. Which error appears, MOVED or CROSSSLOT, depends on whether the keys' slots happen to live on one node. Either way the transaction only works if its keys share a slot. The CROSSSLOT cases are the cleaner evidence.
